# Token 消耗检查与修复范围

## 已确认的浪费

只读解码本机 DSH 持久化事件，未调用付费模型、未修改会话。一个项目会话共有
3,796 次 `doubt_review` 调用：112 次插件生成的合法回执，3,684 次模型主动调用。
后者有 3,683 次返回 `invalid`，另一次结果不是可解析的 JSON。单轮最多 1,253 次。
另一个近期任务会话也存在同类误调用（3 次合法、1 次 invalid）。这些是历史记录，
跨越多个开发版本，不能把全部消耗都归因于当前版本。

修改前源码把内部回执注册为普通模型工具。`operationMaxRounds` 只限制最终草稿打回次数，
模型主动调用这个工具不经过该计数器，因此可以一直“猜回执 → invalid → 再猜”。
每次都会引起主模型下一步请求，重复携带会话上下文。

按当前源码离线重建近期最终回答的审核包，常见约 4.4 万字符，部分接近 12 万字符。
这是输入字符数，不是已计费 token 数。原审核调用没有保存逐次 usage，不能据此给出
真实费用、节省百分比或把所有模型消耗归因于插件。

## 修改

1. 使用宿主 `system-prompt/assemble` 扩展点隐藏内部回执的模型工具定义；不改宿主文件，
   不取消工具注册。合法自动回执仍由 ToolRuntime 执行，并校验会话、轮次、有效期。
2. 对旧上下文引发的模型主动回执调用设确定性后备拦截。混合响应保留其他工具及其回放元数据；
   只有误调用时停止循环、报告尚未完成验证，并阻止旧取证循环再次唤起模型。
   这是异常处理，不会把任务标记为已经解决；该异常仍需用户后续继续任务。
3. 一次审核内记住 reasoning 参数不受支持，供格式修复、紧凑兜底和后续分段复用。
   不跨独立审核缓存，避免切换模型后误用旧能力判断。复合失败样例从 6 次请求降至 4 次；
   真实 token 节省取决于 provider 是否计费失败请求。
4. `EVIDENCE_CONTEXT_LIMIT` 不再删历史重试；没有本轮证据的历史确认也不会在超时后退化成空证据重试。
   含本轮证据的超时恢复仍保留。证据缺口不会因此改为审核通过。
5. 记录每次审核的 `attempt/phase/inputChars/outputChars/elapsedMs/finish/failureCode/usage`。
   usage 只取有限数值字段；缺失为未知。字符数、主模型总消耗和审核用量是不同指标。

未缩小证据包预算、删除常规历史材料、减少补查轮数或改写审核准则。正常审核仍有成本。
没有修改 live 安装、配置或个人会话。

## 后续回归审查

复查确认并修复两处边界遗漏，新增测试先在旧实现失败，再在修复后通过：

- **工具可执行性**：注册表 `get()` 可见不代表宿主允许直接调用。在 PTC 模式中，
  直接调用仅允许 `run_code`，此前改动可能注入无法执行的回执。现在优先使用宿主
  `resolveExecution(name, agent, false)` 判定，保留原有无法自动补查时的处理策略。
  已用真实 ToolRuntime 的 PTC 模式验证；没有声称增加了 PTC 自动补查支持。
- **失败诊断**：最后一次紧凑回退仍返回非法 JSON 时，审核结果正确标记失败，但用量日志
  漏记 `failureCode`。已补齐非法格式与非正常结束的失败码。

另修正 README 引用文档未进入发行包的问题，并加入本地安装复制清单。`npm pack --dry-run`
确认说明文件在包中，`_diag/`、`eval/out/`、`node_modules/` 不在包中。

修复后再次完成全部 `npm run verify`：12 套测试、真实宿主集成（含新增 PTC 边界）、
5 种 AgentLoop 流程通过，独立检查仍为 6 PASS、0 FAIL、0 SKIP。未修改实际安装。
这些检查使用受控模型；在线模型长期表现没有在本次检查中验证。

原有策略仍保留：审核服务失败时会放行原稿，默认 `reviewNotice: off` 不显示审核提示。
本次优化没有把这一策略改成“所有回答必须审核成功才能显示”。
